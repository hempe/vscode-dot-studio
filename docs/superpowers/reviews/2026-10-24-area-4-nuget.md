# Code Review, Area 4: NuGet (2026-10-24)

Scope: `src/services/nuget/` (V3 client, browse/installed/operations/manager services, credentials and feed help, Central Package Management: plan, edits, files, watchers, version properties), `src/core/persistentCache.ts`, `src/core/backgroundRefreshQueue.ts`, `src/services/versionUtils.ts`, `src/services/ownWrites.ts`, the NuGet host handling in `src/webview/providers/NuGetCustomEditorProvider.ts`, and the gRPC install path through `changePackageVersions`.

Method: I read everything in scope in full. I ran the proofs in a copy of the repo (`/tmp/rev4/repo`, `node_modules` symlinked) as jest scratch tests (`src/review/area4*.test.ts`). The HTTP proofs ran against a local HTTPS server with a self-signed certificate (`NODE_TLS_REJECT_UNAUTHORIZED=0`; `TMPDIR` pointed at `/tmp/rev4/tmp`, so the real cache in `/tmp` was not touched), some ran against nuget.org, and some used real `dotnet` 10.0.111 in scratch projects under `/tmp/rev4`. No VS Code was started. The existing tests of the area pass (20 suites, 155 tests). I left out the known bugs, limitations and Not Planned items of `docs/roadmap.md`.

## Findings

### A4-1 (bug, security, proven): feed credentials in cache file names under world-readable `/tmp`, and in error logs

`src/services/nuget/nugetV3Service.ts:98-100` builds the cache key as `${url}|${accessToken}`, where `accessToken` is the `Authorization: Basic` value, i.e. `base64(Username:ClearTextPassword)`. `src/core/persistentCache.ts:142-146` turns the key into the file name, replacing only `+`, `/`, `=` and the URL characters with `_`. `initializeCache` is never called with an extension path (grep: the only call is `nugetV3Service.ts:373` without arguments), so the folder is always `os.tmpdir()/vscode-dotnet-extension/cache/nuget-requests`. On Linux that is the shared `/tmp`. `mkdirSync` and `writeFile` use the default modes, so the folder is 0755 and the files 0644: every local user can list the names and read the private feed's responses. The few `_` in the base64 stand for one of `+`, `/`, `=`, so the token can be recovered by trying the few combinations.

The key, token included, also goes into log lines: `persistentCache.ts:50` (debug), `:54` (warn) and `:80` (`log.error`, shown at the default level; see A4-6, where it happens on every request).

Proof (`area4http.test.ts`, A; search against a local feed with `token:abcdefghijklmnopqrstuvwxyz0123456789SECRETPAT`):

```
A: token dG9rZW46YWJjZGVmZ2hpamtsbW5vcHFyc3R1dnd4eXowMTIzNDU2Nzg5U0VDUkVUUEFU
A: files [ 'https___127.0.0.1_44639_query_q_private_take_20_dG9rZW46YWJjZGVmZ2hpamtsbW5vcHFyc3R1dnd4eXowMTIzNDU2Nzg5U0VDUkVUUEFU.json',
           'https___127.0.0.1_44639_v3_index.json_dG9rZW46YWJjZGVmZ2hpamtsbW5vcHFyc3R1dnd4eXowMTIzNDU2Nzg5U0VDUkVUUEFU.json' ]
A: name contains token: true
A: dir mode 755 file mode 644
A: body on disk: { "data": { "statusCode": 200, "body": "{\"data\":[{\"id\":\"Private.Pkg\",...
```

The developer's machine already has this folder: `ls -ld /tmp/vscode-dotnet-extension/cache/nuget-requests` gives `drwxr-xr-x hempe`, with 140 entries. I did not look at their names. Windows and macOS have a per-user temp folder, so the exposure there is the log only.

Fix: key on a hash of URL and source name (never the token), store under `context.globalStorageUri` (per user, not `/tmp`) with mode 0700/0600, and never log keys.

### A4-2 (bug, security, proven): shell injection through package ids, versions and project paths

`src/services/nuget/packageOperationsService.ts:22-40, 91, 138, 189-199, 285, 305` and `packageInstalledService.ts:60, 308` build strings for `exec` (which runs `/bin/sh` or `cmd.exe`). The package id, version, source and framework go in without quoting; the project path is wrapped in `"` only. Inside double quotes `$VAR`, `` `cmd` `` and `$(cmd)` still expand on POSIX, and `%VAR%` on Windows. Where the values come from:

- The id comes from the webview message (`NuGetCustomEditorProvider.ts:455-469`, from a search result of any configured feed or from A4-3's cache), or from the project file (uninstall of a `PackageReference Include` of a cloned repository).
- The version comes from the webview.
- The project paths come from the webview.

The host does not validate any of them (`validatePackageOperation` exists in `nugetManagerService.ts:357` but is never called).

Proof (`area4unit.test.ts`, L, real `/bin/sh`):

```
uninstallPackage('<dir>/App.csproj', 'Foo;touch <dir>/pwned')
L: uninstall success true marker exists: true
```

`dotnet remove` fails, `touch` runs, the shell's exit code is 0, and the result reads "Successfully uninstalled". On Windows `&` does the same in `cmd.exe` (not run).

Fix: `execFile('dotnet', [...args])` (no shell), and validate the id (`^[A-Za-z0-9_.-]+$`, as NuGet does) and the version (NuGet version or range) on the host.

### A4-3 (bug, proven): the persistent cache is trusted at any age and from anyone

`nugetV3Service.ts:389-412`: a persistent entry is returned whatever its age (`maxAge: 30 min` in `initializeCache` is never read; `persistentCache.ts` has no use of `options.maxAge`). Stale entries are only refreshed 60 s later in the background (`backgroundRefreshQueue.ts:10, 39-61`, where the comment says 5 s). Nothing checks who wrote the file or that its stored `url` matches the key. Because the folder is in shared `/tmp` (A4-1), another local user can create it first, or drop files into it.

Proof (`area4plant.test.ts`, Q): I planted two files dated a year back, one for the nuget.org service index (pointing search to `https://planted.invalid/query`) and one for that search:

```
Q: ["Newtonsoft.Json;touch${IFS}/tmp/x"]
```

The planted results are shown, with no network request. Installing that "package" runs the command (A4-2). The same staleness without an attacker: a version published to the private feed an hour ago is not offered until a refresh 60 s after the first look, and the UI then has to re-ask.

### A4-4 (bug, proven): SemVer 2.0.0 versions are missing on nuget.org

`nugetV3Service.ts:338-350` takes the first resource whose `@type` contains `RegistrationsBaseUrl`. On nuget.org that is `https://api.nuget.org/v3/registration5-semver1/`, which leaves out every SemVer 2.0.0 version (dotted prerelease labels, build metadata, and packages that depend on such versions). The NuGet client uses `RegistrationsBaseUrl/3.6.0` (`registration5-gz-semver2`, gzip). `buildSearchUrl` (`:355-365`) does not send `semVerLevel=2.0.0` either (nor `prerelease`; Browse only shows packages that have a stable version, and their latest stable version).

These details drive the Installed versions, Updates (`nugetManagerService.ts:253-261`) and Consolidate.

Proof (`area4http.test.ts`, H, nuget.org):

```
H: Refit.HttpClientFactory latest 15.2.0 versions 60
H: Serilog.Exceptions latest 5.4.0 versions 24
H: Hangfire.PostgreSql latest 1.20.0 versions 44
```

nuget.org's search with `semVerLevel=2.0.0` gives 16.4.0, `8.4.0+build.694` and `1.21.1+1` for these. Without it the search gives 15.2.0, 5.4.0 and 1.20.0 (the same query with and without the parameter, by `curl`). A project on Refit.HttpClientFactory 15.x is shown as up to date. The same goes for MassTransit 5.5.6 packages and others found in a sample of 20 queries.

Fix: prefer `RegistrationsBaseUrl/3.6.0` (handle gzip), else `/Versioned`, else the plain one. Send `semVerLevel=2.0.0`, and `prerelease` as chosen in the UI.

### A4-5 (bug, proven): cache key collisions

`persistentCache.ts:144` maps every character outside `[A-Za-z0-9-_.]` to `_`, so different keys share a file: `q=foo+bar` and `q=foo_bar`, path `/a/b` and `/a_b`, also `…|` (no token) against a token starting with the same characters. `get` does not compare the stored `url` with the key.

Proof (`area4http.test.ts`, B; a new module instance in between, as after a restart):

```
B: first [ 'ResultFor(foo bar)' ] second [ 'ResultFor(foo bar)' ] requests [ '/v3/index.json', '/query?q=foo+bar&take=20' ]
```

The search for `foo_bar` never reached the server. Fix: hash the key (A4-1) and keep the full key in the entry, compared on read.

### A4-6 (bug, proven): long keys are never cached, and their error logs the token

`persistentCache.ts:71-80`: a file name over 255 bytes fails with `ENAMETOOLONG`. An Azure DevOps search URL (`https://pkgs.dev.azure.com/<org>/<project>/_packaging/<feed>/nuget/v3/...?q=...&take=20...`) plus `|` and the base64 of `token:` with a 52-character PAT easily goes over that.

Proof (`area4http.test.ts`, C, key of 291 characters): no file was written (0 matching files), and the log shows

```
[ERR] PersistentCache: Failed to write cache entry https://127.0.0.1:46065/contoso-engineering/.../index.json?q=microsoft.extensions.dependencyinjection.abstractions&take=20&skip=0&prerelease=false|dG9rZW46YWFhYWFh...
```

So the private feed is fetched again on every visit after the 5-minute memory cache, and each failure puts the credentials into the log at error level.

### A4-7 (bug, proven): success decided by `includes('error')`

`packageOperationsService.ts:49, 100, 148, 207, 252`: `success = !stderr.includes('error') && !stdout.includes('error')`. Any path, package id, feed URL or info line with lowercase `error` makes a successful command count as failed. The opposite also happens: a failing command whose output only has `Error` or `NU1101` still counts as succeeded (the exit code is not used; `exec` rejects on a non-zero exit, so the check is redundant anyway).

Proof (`area4cli.test.ts`, M, real `dotnet` with a local feed, project `/tmp/rev4/error-pages/App/App.csproj`):

```
M: success false csproj has it: true
M: Failed to install Rev4Lib: info : X.509 certificate chain validation will use the fallback certificate bundle at ...
```

Effects: an error toast after a working install. Also `changePackageVersions` (`centralPackageOperations.ts:216-220`) leaves the project out of `cliUpdated`, so it is not evaluated again and the tree and editor keep the old version. The gRPC path (`grpcReferenceService.ts:263-268`) and the WCF path also report failure. Fix: rely on the exit code (`exec` already rejects on non-zero).

### A4-8 (bug, proven): source listing parses English output only

`packageBrowseService.ts:123` matches `\[(Enabled|Disabled)\]`. `dotnet` follows the OS language (`LANG`, or the Windows UI culture): `LANG=de_DE.UTF-8 dotnet nuget list source --format detailed` prints `1.  PrivateFeed [Aktiviert]`. Nothing matches, so the fallback runs (`:180-245`). It reads `nuget.config` (lower case only) under `process.cwd()` (VS Code's cwd, not the workspace), runs `find .` from that cwd (on Windows `find` is the text-search tool), and ends with nuget.org alone.

Proof (`area4src.test.ts`, O, workspace `/tmp/rev4/ws/src` with a `NuGet.Config` naming `PrivateFeed`):

```
O: LANG en_US.UTF-8 ... -> ["PrivateFeed","nuget.org"]
O: LANG de_DE.UTF-8 ... -> ["nuget.org"]
```

On a German, French and so on system, Browse, Updates and details never look at the private feed. Fix: run with `DOTNET_CLI_UI_LANGUAGE=en`, or read the configs with `nugetConfigFiles` (already written for credentials) and the `<packageSources>`, `<clear/>` and `<disabledPackageSources>` sections.

### A4-9 (bug, proven): sources from the workspace folder, credentials from the solution folder

`packageBrowseService.ts:108-112` runs `dotnet nuget list source` with `cwd` = the workspace folder (`solutionWorkspaceFolder()`). `feedAuth.ts:14-17` reads credentials starting in the solution's folder, and `dotnet restore` and `dotnet add` use the project's folder. A repository with `src/App.sln` and `src/NuGet.Config` opened at the repository root:

```
--- cwd=workspace root
0      (PrivateFeed not listed)
--- cwd=solution dir
1
```

Restore works, but the NuGet manager's Browse, Updates and details only see nuget.org. Fix: list from `configStartDir()`. Per project would be more exact; NuGet uses the project's folder.

### A4-10 (bug, proven): reading NuGet.Config credentials

`src/services/nuget/nugetCredentials.ts:55, 72-90`:

1. `attribute()` returns the raw attribute text, while `setClearTextPassword` (`:107, :116`) escapes `&<>"`. A password `pa&ss<word` entered through "Enter New Token..." is stored correctly, as NuGet expects, but read back as `pa&amp;ss&lt;word`, so the header is wrong and the feed answers 401 again. It also misreads a correct hand-written `&amp;`.
2. XML comments are not skipped. With the old token kept commented out after the new one, the old one is used.
3. Single-quoted attributes (`value='...'`, valid XML) are not found.

Proof (`area4unit.test.ts`, I and J):

```
I: written <add key="ClearTextPassword" value="pa&amp;ss&lt;word" />
I: header decodes to me:pa&amp;ss&lt;word
J: {"kind":"clearText",...,"password":"OLD-EXPIRED-TOKEN"}
J: single quotes: {"kind":"none"}
```

Azure DevOps and GitHub PATs are alphanumeric, so item 1 affects passwords and some other feeds' tokens. Item 2 affects anyone who keeps the old line. Fix: unescape the entities (`Xml.unescape` exists in `projectFileEditor`), and skip `Xml.ignoredRanges` (comments).

### A4-11 (bug, proven): prerelease comparison

`src/services/versionUtils.ts:113-123`: when both versions are valid semver, `semver.compare` is used, and it compares prerelease labels case-sensitively (ASCII). NuGet compares them case-insensitively. The non-semver fallback (`:130-163`, 4-part versions) drops the label entirely, and `isPrerelease` (`:82-98`) only knows `-alpha`, `-beta`, `-rc`, `-preview`, `-pre` and `-dev` for 4-part versions; NuGet treats any `-label` as prerelease.

Proof (`area4unit.test.ts`, K):

```
K: newest of beta2/RC1: 1.0.0-beta2 isOutdated(RC1 -> beta2): true
K: isPrerelease 4.6.0.1-ci0042: false  1.2.3.4-nightly: false
K: compare 1.2.3.4-beta vs 1.2.3.4: -0
```

So with prereleases shown, a project on `1.0.0-RC1` is offered an "update" to `1.0.0-beta2`. A 4-part CI build such as `4.6.0.1-ci0042` is offered as a stable update with prereleases hidden. Fix: one NuGet-style comparer (numeric parts of any length, label case-insensitive, any `-` means prerelease).

### A4-12 (bug, proven): multi-byte characters broken at chunk boundaries

`nugetV3Service.ts:481-482`: `data += chunk` decodes every `Buffer` chunk on its own. Proof (`area4http.test.ts`, D, the body sent in two writes split inside `ü`):

```
D: description "Z��rich café ünïcode"
```

Large registration pages arrive in many chunks, so descriptions, authors and titles with non-ASCII characters break at random. Fix: `res.setEncoding('utf8')`, or collect the Buffers and `Buffer.concat` them.

### A4-13 (risk, proven): HTTP handling

`nugetV3Service.ts:454-500`:

- **Only `https`.** `https.request` is used whatever the scheme. An `http://` feed (local BaGet, a test server) fails with `SSL routines:...:wrong version number` (E). The NuGet CLI warns about http but uses it.
- **No redirects.** A `301` for the service index gives "Failed to fetch service index, status code: 301" (E). Feeds behind a moved host or a proxy redirect fail, where NuGet follows.
- **No size limit, only an idle timeout.** `setTimeout(30000)` fires after 30 s without data, so a slow-dripping response never ends. There is no cancellation either (a closed editor keeps its requests).
- **Credentials sent up front to any host.** The Basic header goes on every request of a source, including to hosts the service index names (F: `localhost:40877`, another host, got `Authorization: Basic dTpzZWNyZXQ=`). NuGet answers challenges, and .NET drops the credentials on cross-host redirects. A feed's own index normally stays on its host, so this is a risk, not a bug.
- **Proxy.** VS Code's `http.proxySupport` patches Node's `https` in the extension host, so the request probably goes through the proxy. I did not verify this in VS Code.

### A4-14 (risk, proven): a failing source holds each lookup for 6 s

`nugetV3Service.ts:177-248`: each source gets 3 attempts with `1000 * (i + 1)` ms backoff after an exception. A local folder source (`isLocal`, listed by `dotnet nuget list source`, e.g. the default "Microsoft Visual Studio Offline Packages" on Windows) throws in `new URL(...)` every time. An `http://` source or one that cannot be reached does the same.

Proof (`area4http.test.ts`, G, a local folder first, then a working feed):

```
G: version 1.0.0 took 6034 ms
```

This happens per package. `PackageSharedService` runs 10 at a time and retries 3 times on top, so an Installed tab with 60 packages waits about 36 s before any metadata shows. Also, `return null` when a source has no registration resource (`:187-190`) stops the loop before the next source. Fix: skip local sources (or read the `.nupkg` files), don't retry what cannot succeed, and `continue` to the next source.

### A4-15 (bug, proven): unquoted `GetPathOfFileAbove` is not followed

`src/services/nuget/centralPackageFiles.ts:318` requires `'...'` around the arguments. The CPM documentation shows `<Import Project="$([MSBuild]::GetPathOfFileAbove(Directory.Packages.props, $(MSBuildThisFileDirectory)..))" />` without quotes, and MSBuild accepts it: in `/tmp/rev4/cpm`, the nested `src/Directory.Packages.props` imports the parent this way, the parent defines `RevVersion`, and `dotnet msbuild -getItem:PackageVersion` evaluates `Rev4Lib` to `1.0.0`.

`importChain` stops at the nested file, so `findVersionProperties` refuses (`area4chain.test.ts`, P):

```
P: chain [ '/tmp/rev4/cpm/src/Directory.Packages.props' ]
P: found [{"property":"RevVersion","refusal":"notFound",...}]
```

The user is told `$(RevVersion)` "is not defined in Directory.Build.props, Directory.Packages.props or a file they import" and can only replace it with a literal. The roadmap's Not Planned item says imports through `GetPathOfFileAbove` are handled, so this form is a gap in what the docs promise. The same gap applies to the watchers of files in that chain with other names, and to `declaredGlobals`.

### A4-16 (risk, proven): four `dotnet list package` runs per project load

`NuGetManagerService.getProjectNuGetData` (`nugetManagerService.ts:292-327`):

- `getProjectInfo` → `getProjectPackages` and `getProjectFramework`.
- `getGroupedInstalledPackages(isProject)` → `getProjectPackages` again.
- `getGroupedOutdatedPackages(isProject)` → `getGroupedInstalledPackages` again.

Proof (`area4count.test.ts`, N, `exec` counted):

```
N: 4 commands
N: dotnet list "App.csproj" package --format json
N: dotnet list "/p/App.csproj" package --framework net8.0 --format json 2>/dev/null || dotnet list "/p/App.csproj" package --format json
N: dotnet list "App.csproj" package --format json
N: dotnet list "App.csproj" package --format json
```

Each run takes about 1.1 s on the scratch project (`time dotnet list ...`), and the load repeats after every evaluation burst (`NuGetCustomEditorProvider.ts:47-65`). `getProjectFramework` asks for `net8.0` whatever the project targets, and its `2>/dev/null` is POSIX-only syntax (on `cmd.exe` the redirection fails and the `||` branch runs).

Suspected, not run in the UI: in the project context `installedPackages` comes from `getProjectPackages` without `withVersionSources`. `versionLabel(maxInstalled)` (`PackageList.tsx:275`) would then lack the "(override)"/"(global)" suffix there; `projectInfo.packages` has the sources.

### A4-17 (risk, proven by code): README and icon of private packages from nuget.org

`NuGetCustomEditorProvider.ts:735-789` always builds `https://api.nuget.org/v3-flatcontainer/<id>/<version>/icon|readme`. A private package's id and version go to nuget.org from the webview. If nuget.org has a package with the same id (squatted or unrelated), its README and icon are shown for the private package. Fix: take the feed's `PackageBaseAddress` (and `ReadmeUriTemplate`), or show nothing for packages that are not from nuget.org.

### A4-18 (cleanup, proven by code)

- `PersistentCache` `maxAge` is never read, and `NuGetV3Service.initializeCache(extensionPath)` is never called with a path (A4-1, A4-3).
- `NuGetV3Service.getPackageVersions` (`:256-285`) is unused, and it would send a private feed's token to `api.nuget.org`. `PackageOperationsService.addPackageReference`, `clearCache`, `verifyPackageInstalled` and `getPackageStatus` are unused. So are `NuGetManagerService.validatePackageOperation` and `getContextFromPath` (grep outside tests).
- Every cache miss is logged with `log.error('Making fresh request ...')` (`nugetV3Service.ts:416`), and every queue step with `log.error('Processing background refresh ...')` (`backgroundRefreshQueue.ts:105`). The Error level is meant for errors.
- `BackgroundRefreshQueue`'s comment says "5 second delay"; `DELAY` is 60 000. The queue's timers are not cleared on deactivate.
- `searchAcrossConfiguredSources` (`packageBrowseService.ts:305`) takes `sources.slice(0, 3)` before skipping disabled sources: with two disabled sources ahead of it, the fourth (enabled) one is not searched.
- `getPackageDetails` caches by package id alone for 10 minutes (`nugetV3Service.ts:153`): after a `NuGet.Config` change, details still come from the old sources. It also reads only the 2 newest registration pages (`:219`), so older versions are missing from the version lists of packages with more than 256 versions.
- The `PackageSharedService` retry (`:411-426`) never retries: `PackageBrowseService.getPackageDetails` catches everything and returns `null`.

## Checked and fine

- **CPM edits** (`centralPackageEdits.ts`, `centralPackageFiles.applyPackageEdits`): every file is edited in memory first; an edit that fails leaves all files untouched, and a write that fails restores the files written before it. Comments and targets are skipped, ids compare case-insensitively, and line endings and BOM are kept (`utf8` read and write round-trips a leading U+FEFF).
- **`OwnWrites`** (`mtime|size` stamp) leaves only the extension's own write to the watchers. A later edit, or the rollback's write, is evaluated again. The map is bounded by the number of distinct files.
- **`planVersionChange`, `planUninstall`, `planConsolidate`**: I re-read them against the d91e6c5 fixes. Global packages, opt-outs, overrides, inherited references (no "Set for this project only"), multi-targeted or unevaluated projects (no orphan prompt) and the confirmation texts behave as documented. I did not see regressions from `versionProperties` (one answer per property, conflicts refused, project-file definitions refused as "differs").
- **The gRPC install path** (`installGrpcPackages` → `changePackageVersions(..., 'shared')`) asks before changing a central version used by other projects, and returns a cancelled result. It inherits A4-2 and A4-7 through `installPackage` for projects without CPM.
- **Timeouts**: every `exec` in the area has one (10 s to 180 s), and `withProgress` callers send a completion message in every branch.
- **Rejected credentials** (`reportRejectedCredentials`): one message per source, credential and minute, the password never shown, and new tokens written to the user config rather than the repository's file. `feedHelp` builds only `https` URLs for known providers.
- **`watchPlan` and `CentralPackageWatchers`**: watchers are disposed when the set changes and on dispose; files outside the workspace are re-checked on focus as documented.

## Not reviewed / limits of this review

- **Windows** (not run): `cmd.exe` behaviour of A4-2 (`&`, `%VAR%`), `2>/dev/null` in A4-16, the `find .` fallback, `%AppData%` user config. Everything here was run on Linux.
- **VS Code itself** was not started: the proxy behaviour of `https` in the extension host (A4-13) and the label suspicion in A4-16 are unverified in the real UI.
- **Azure Artifacts Credential Provider**: I did not test how it interacts with the V3 client (the client never uses it; that is a documented limitation).
- **`packageGraph.ts` and `packageNodes.ts`** were only read, not run; the webview side of the NuGet manager is area 3.
- **The A4-3 chain** (planted cache to command execution) was proven in two halves (Q: planted id returned; L: such an id executes); the click in the UI between them was not driven.
