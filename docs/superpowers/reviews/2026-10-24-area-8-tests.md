## Findings

### A8-01 (risk, proven by mutant M14): no test notices when F# projects are no longer recognised as projects

`parsers/solutionFileParser.ts:351`: `isDotNetProject` decides which solution entries become projects (`:112`, `Solution.ts:292`, `solutionService.ts:103`). Mutant: remove `fsproj` from the regex; `tsc` is clean, `npx jest --findRelatedTests src/parsers/solutionFileParser.ts` runs 401 tests and all pass. No fixture or test contains a `.fsproj` entry in a `.sln`. Scenario: a refactoring of that regex silently drops every F# project from Solution Explorer. Fix: one test with an `.fsproj` (and `.vbproj`) project line in `solutionFileParser`.

### A8-02 (risk, proven by mutants M01, M02): `VersionUtils` non-semver paths are untested

`services/versionUtils.ts:136` (4-part versions like `1.2.3.4` vs `1.2.3`: `Math.max` -> `Math.min` survives, so `1.2.3.1` is "equal" to `1.2.3`, hence no update offered) and `:96` (`-pre`/`-dev` fallback). The only test importing it is `packageVersions.test.ts`; 45 suites relate but none covers 4-part versions. This drives "outdated" markers and "latest version" in the NuGet manager. Fix: table tests for `compare`/`isOutdated`/`isPrerelease` with 4-part and non-semver values.

### A8-03 (risk, proven by mutant M09): the NuGet V3 cache key test does not check the token

`nuget/nugetV3Service.ts:378`: `getCacheKey(url, accessToken)` -> `getCacheKey(url)` survives (140 tests). A4-1/A4-6 concern the key as well: cached results of an authenticated feed could be served to a request without (or with another) token, and no test would show it. The file has 34.9% line coverage (173 uncovered lines, `:347-549`).

### A8-04 (cleanup, proven by mutant M03): linked-file drop target rule untested

`core/dropRules.ts:66`: removing `itemState === 'linked'` as a drop-target exclusion survives (148 tests); `dropRules.test.ts:16` only covers a linked file as a dragged node.

### A8-06 (cleanup, proven): 47 build artifacts of `test-solution` are tracked despite `.gitignore`, and any `dotnet build` there dirties the tree

`git ls-files src/__fixtures__ | grep -E '/(obj|bin)/'` lists 47 files (`ClassLibrary/obj` 23, `Tests/obj` 12, `WebApp/obj` 12, `Tests/bin` 1), committed in `dcbf17c` before `**/obj/` and `**/bin/` were ignored (`git check-ignore -v` confirms the rule matches). They hold the machine state of whoever built last: `ClassLibrary.AssemblyInfo.cs` embeds the commit hash (`1.0.0+401f956c...` now instead of `4f95b2d...`), `Tests.GlobalUsings.g.cs` differs by SDK version (`global using global::System;` vs `global using System;`), and 21 tracked files contain the committer's absolute path `/home/hempe/...` (`git grep -l /home/ -- src/__fixtures__`). That is the 30 `M`/`D` lines in the opening `git status`.

Proven that the tests do not need them and do not write them: in the scratch copy I deleted every `obj`/`bin` under `test-solution` and `npx jest src/parsers` (the only suites that read this fixture: `projectFileParser.spec.ts`, `solutionFileParser.spec.ts`, `netFramework.spec.ts`) passes 29/29; and after the full suite (169 suites, with real `dotnet`) `diff -r` of the scratch fixtures against `git archive HEAD` shows no change in any tracked file. So the dirty files come from a manual or tool `dotnet build` in the repository, not from `npm test`. Fix: `git rm -r --cached` the 47 files.

Minor: an empty untracked directory `src/__fixtures__/test/unit/services/projectItems` (created 2026-10-21) exists in the real tree; running `src/test/unit/services/projectItems` again did not recreate it, so the creator is unknown (suspected an earlier version of a test resolving a path relative to the fixtures root).

### A8-07 (risk, proven in the CI log): tests that cannot run report PASS, and in CI two of them never run

Pattern: the test body starts with `if (!hasDotnet || restore failed) { console.warn('... skipping'); return; }` and ends green. Jest counts it as passed, not skipped. Sites: `testing/testExplorer.dotnet.test.ts:196,216,243,269`, `testing/runSettings.dotnet.test.ts:139`, `serviceReferences/serviceReferenceGenerator.svcutil.test.ts:19-21`, `grpc/protobufReferences.msbuild.test.ts:57` (nuget.org unreachable). The other dotnet tests use `test.skip` (visible as skipped), which is the right form.

Proof, log of CI run 40090465048 (`gh run view --log`), both `ubuntu-latest` and `windows-latest`: `PASS src/test/unit/services/testing/testExplorer.dotnet.test.ts` followed by `console.warn: Windows, or dotnet, mono or the test packages are not available, skipping` (the Mono test: CI has no Mono, `ci.yml` does not install it), and `PASS ...serviceReferenceGenerator.svcutil.test.ts` with `dotnet-svcutil not installed, skipping`. Summary line of ubuntu: `Tests: 1521 passed, 1521 total`, i.e. 1521 "passed" including these. So the Mono vstest path (A5-3/A5-4 code) and the real svcutil run (A6-2/A6-3 code) have no automated coverage anywhere, and a broken NuGet restore (feed down, A4-14 style) would turn the four Test Explorer tests silently into no-ops.

Fix: `const run = condition ? test : test.skip` everywhere; for restore failures `throw` when `process.env.CI` is set; install Mono and `dotnet-svcutil` in the CI job or state in `docs/manual-testing.md` that these two are manual.
